▶

Goal: from toy GPT to the actual modern pipeline — and the four disciplines that separate rigor from vibes: architecture literacy, data work, evaluation design, and RL. Note the order: eval design comes BEFORE fine-tuning, on purpose.

1 The real pretraining recipe

  • D1–4Karpathy — build-nanogpt (reproduce GPT-2 124M: mixed precision, LR schedules, real data loading) CORE
  • D5–6EleutherAI — Transformer Math 101 (params, FLOPs, memory — the arithmetic of scale) SURVEY

2 From GPT-2 to 2026: modern architecture + scaling laws

Why this step exists: Phase 2 and Step 1 hand you a GPT-2 — a 2019 design. Everything you actually use has moved on, and the differences are not cosmetic. Skip this and Phase 6's inference economics won't land, because you won't know what a KV cache is.

  • DAY 1Raschka — The Big LLM Architecture Comparison for the baseline delta from your GPT-2: RoPE, RMSNorm, SwiGLU, GQA/MLA CORE · go to the RoPE and GQA papers REF only if a detail nags
  • DAY 2Now bring it current — the field moved again while that article was being written. Raschka — A Visual Guide to Attention Variants (MHA → GQA → MLA, sparse and hybrid) CORE + Recent Developments in LLM Architectures (KV sharing, compressed attention, how 2026 models attack long-context cost) SURVEY. Keep the LLM Architecture Gallery REF as the living reference
  • DAYS 3–4Mixture-of-Experts: HF — MoE Explained + Grootendorst — A Visual Guide to MoE. How most frontier models are now built: total params ≫ active params — the fact that drives training cost, serving cost, and why "how big is it?" stopped being one number CORE
  • DAY 5The KV cache — what it holds, why it grows with context × batch, and why it (not the weights) usually decides how many users fit on a GPU. Compute one by hand for a model you use: 2 × layers × kv_heads × head_dim × seq_len × batch × bytes. This is the object Phase 6 · Steps 3–4 are really about CORE
  • DAY 6Scaling laws — Epoch AI's literature review, then the shape of the argument: Kaplan (2020) → Chinchilla (2022) → the modern correction that inference cost sets the real optimum (Go smol or go home). The bridge from Layer 3 to Layer 0: it's why data centers are the size they are CORE
  • DAY 6bThe durable skill — Raschka's My Workflow for Understanding LLM Architectures. Everything above is a snapshot with a shelf life; this is the method for reading the next release yourself. Of everything in this step, it's the part that won't expire CORE
Milestone · same day

Write ~200 words on "how does the model I use daily differ from the GPT-2 I built, and why does each difference exist?" If you can't, re-read before moving on. Architecture literacy is what makes every later phase readable.

  • D1–2HF LLM Course fine-tuning chapters SURVEY

Milestone — the full honest loop

data pipeline → frozen eval → baseline → fine-tune → re-measure → write-up including what did NOT improve. Most people fake this loop; you're building the muscle to do it for real.

6 Post-training I: SFT → preference alignment

  • D1–4smol-course — ~20 hr, six units; GPU recommended. Do instruction-tuning + preference-alignment units now; rest later SURVEY
  • D5–6Nathan Lambert — RLHF Book (intro + reward models + DPO chapters). Know why DPO exists and where it stops being enough CORE

7 Post-training II: reasoning + RL with verifiable rewards

Why this got its own step: post-training is where differentiation happens now, and RLVR is the fastest-moving layer in the entire stack. It's also the direct answer to "how did reasoning models get good," which one skimmed paper cannot give you.

  • D1–2Raschka — Understanding Reasoning LLMs + skim the DeepSeek-R1 paper SURVEY (precision: R1-Zero = reasoning from pure RL with verifiable rewards; production R1 used cold-start data + multi-stage training), then RLHF Book ch. 14 — Reasoning & RLVR for the mechanics CORE
  • DAY 3GRPO — how it differs from PPO (no learned value model; advantage estimated from a group of sampled completions) and why that made RL post-training cheap enough to spread. TRL's GRPO Trainer docs are the concrete reference CORE
  • D4–5Hands-on — run a small GRPO job on a verifiable task (math with a checkable answer, or code with a passing test) via Unsloth's RL guide free Colab (~$5–20). The point is not a good model; it's watching a reward curve respond to a reward function you wrote CORE
  • DAY 6Environments & reward hacking — skim open-r1 and verifiers for how RL environments are structured, then think adversarially: for the reward you wrote on Day 4, what is the laziest policy that scores well without solving the task? Write it down. Reward hacking is the field's central practical problem and you should meet it with your hands on a real reward CORE
  • Current as you read it — Raschka's Categories of Inference-Time Scaling and Controlling Reasoning Effort in LLMs cover how reasoning became controllable (low/medium/high effort modes) — the part that reached products fastest. Lambert's frontier post-training recipe review is the best look at what labs actually run SURVEY

Production AI Systems↑ UP · 3 STEPS · DEMOS → PRODUCTS

Goal: the AI-specific operational layer. Core, not elective, for one reason: you ship apps to real users. (A pure researcher could skip it; you can't.)

Gate — answer honestly first

Can you containerize an API, run tests in CI, manage secrets, deploy a service, authenticate requests? All yes → compress this phase, jump to Step 3. Mostly no → short general software-production bridge first (a solid Docker + CI/CD tutorial for your stack), then return.

  • D1–4Huyen's AI Engineering serving/optimization chapters, re-read as an operator: streaming, retries/timeouts/idempotency, caching, routing & fallbacks, budget enforcement CORE
  • D5–6Prompt caching — precision matters: cache-hit input tokens cost ~90% less, but cache writes cost more and output tokens are unaffected. It slashes the repeated-context slice of the bill, not the bill. Measure your app's cacheable fraction CORE

  • D1–3Prompt/model/dataset/experiment versioning — wire your Phase 4 eval suite into CI as a gate: no prompt or model change ships without evals passing CORE
  • D4–6Observability: structured logs/traces/metrics for LLM calls (OpenTelemetry = durable vocabulary; LangSmith/Braintrust-style tools = implementations). Online quality monitoring & drift SURVEY

3 The project (on YOUR existing deploy stack)

  • ALLTake the Phase 4 capstone app, deployed however you already deploy (Vercel, Railway, a VPS — no new infra required), and add: eval-gated deploys, per-request cost + latency logging, a cache layer, a simulated provider outage (revoke the API key — what does the user see?), and a documented, tested rollback path CORE
How you'll know it worked

You can answer "what does a request cost, what's p95 latency, and what happens when the provider goes down?" with measurements and a demonstration, not guesses. Load-test with k6 if you want real numbers.

2 Distributed training II: what actually happens

Why this step exists: Step 1 teaches the parallelism strategies. It does not teach you that large runs fail constantly, that a node dies mid-epoch, that your throughput is 40% of theoretical and you have to find out why. That gap is the difference between reading about training and training.

  • D1–3Stas Bekman — ML Engineering, selectively: performance/throughput debugging, fault tolerance, training instabilities. The field manual — written from real large-run scar tissue, not theory CORE
  • D4–5HF — The Smol Training Playbook: one team's honest end-to-end account of training a real model, including the ablations that failed. Read it right after the theory, while you still believe training is tidy CORE
  • DAY 6Low precision + collectives — why FP8 training is standard and what it costs in stability, plus the collectives everything is built from: all-reduce, all-gather, reduce-scatter (NCCL). Name the collectives and "the interconnect is the bottleneck" in Step 5 becomes a concrete claim instead of a slogan SURVEY

3 Inference: the economics of serving

  • D1–2kipply — Transformer Inference Arithmetic (predict latency + cost from first principles) CORE
  • DAY 3Prefill vs decode — the single most useful distinction in serving: prefill is compute-bound and parallel, decode is memory-bandwidth-bound and sequential. Nearly every 2026 optimization (continuous batching, chunked prefill, prefill/decode disaggregation onto separate GPU pools, KV-cache-aware routing) follows from those two workloads wanting opposite hardware. NVIDIA's inference-optimization guide CORE
  • DAY 4Gordić — Inside vLLM (paged attention, continuous batching, speculative decoding) + skim SGLang for a second engine's take (RadixAttention / prefix-cache reuse). Two engines is what turns "how vLLM works" into "how serving works" CORE
  • D5–6Grootendorst — A Visual Guide to Quantization CORE + BentoML LLM Inference Handbook REF

4 Serve a model yourself (Capstone #2, heavier rubric)

  • D1–4Deploy an open model with vLLM on a rented GPU. Measure tokens/sec; try a quantized version; compute cost-per-million-tokens vs an API. Report throughput and latency separately at more than one concurrency level — a single number here is almost always misleading CORE
  • D5–6Read the original vLLM PagedAttention post — it maps onto what you just ran, and onto the KV cache you computed by hand back in Phase 3 · Step 2 SURVEY

PROTOCOL

How to Use This Plan

  1. Track progress here — checkboxes save to this browser. The markdown files remain the source of truth for editing.
  2. Core > Survey > Reference is the pressure valve. Behind schedule? Surveys become skims, references get skipped. The CORE spine is non-negotiable; everything else flexes.
  3. Projects > completion. Skipping a step of videos to finish a milestone is always the right trade.
  4. When stuck, switch resources, not topics. Every topic has 2–3 alternative explainers in the library below.
  5. Dependencies: 0 → 1 → 2 → 3 is the hard chain (Phase 3 · Step 2 needs Step 1's GPT-2). 4 → 4.5 go together; 5 and Part 2 branch off 2–3; 6 wants 5 and Phase 3 · Step 2's KV cache. In Part 2: D before E; A before B is nice; F needs all of Phase 1; G wants Phase 3; C floats free. The real branch point is the end of Phase 3 — from there every track is profitably open, so if one is calling louder than the next phase, take it.
  6. Budget: ~$150 books (all three) + possibly ~$49 one Coursera month + $60–180 GPU/API credits (incl. ~$10–30 Track E sim, ~$5–20 Phase 3 GRPO) + optional ~$100 nanochat + optional ~$100–300 SO-101 arm. Everything else free.
  7. Use AI to learn AI. Ask Claude to quiz you, re-explain stuck concepts, or review your micrograd. Just write the code yourself first.
  8. Retention. Without a review loop you won't remember Phase 2 by the time you reach Phase 6, and the later phases quietly depend on the earlier ones. Two cheap habits (~8 hr total): keep a NOTES.md per phase (three bullets a week — what clicked, what didn't), and at every phase boundary spend one hour re-deriving something from two phases back from a blank file. If you can't, that's the review loop doing its job.
  9. The Pre-Phase Audit Protocol. Before starting any phase or track, ask Claude: "Audit Phase N first." The audit verifies every link, re-checks availability claims, and — critically — asks whether the practice changed, not just whether the link resolves. The real decay mode is a resource that loads perfectly while teaching a superseded default (chunking-heavy RAG written for 8k context windows; PPO-shaped RLHF written before GRPO; dense-model assumptions written before MoE went mainstream). Of each CORE item ask: is this still how it's done, or just still online? Then research what's genuinely new (filtered by the end-to-end-systems principle), propose a diff, update the files + this page. Depth by volatility — stable (skip / 5-min check): Phases 0–2, math, Track D foundations, Track F · medium (light audit): Phase 3 Steps 1, 3–6; Phase 5; deep RL · fast-moving (full audit): Phase 3 Steps 2, 6–7; Phases 4, 4.5, 6 and Tracks A, B, C, E, G.
